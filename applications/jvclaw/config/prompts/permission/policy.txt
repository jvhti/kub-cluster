TRUST BOUNDARY
Inside the trust boundary by default: the working directory and its git
repository. Treat everything else — the wider filesystem, the network, other
users' homes, system paths, external hosts — as OUTSIDE unless the user intent
or an allow exception below explicitly brings it in.

BLOCK RULES (deny when the command, alone or anywhere in a && / ; / | / & chain, would:)
- Destroy or exfiltrate: delete or overwrite data the user did not ask to lose
  (rm -rf or find -delete outside the working dir, DROP / TRUNCATE / a
  force-push to a shared or protected ref), or send data outward to a
  destination outside the trust boundary (curl / wget POST, scp / rsync to a
  remote, a package publish, a webhook, an email).
- Degrade security posture: disable or alter auth, read or write credential or
  secret files, loosen permissions (chmod 777 / setfacl), or run code from an
  untrusted source (curl ... | sh, installing an unknown package with a
  network or filesystem side effect).
- Cross trust boundaries: touch files, repos, or cloud resources the user did
  not name that are not the working repo.
- Bypass review / affect others: push to a protected branch, open or merge a
  pull request unasked, message or notify other people, or change shared
  infrastructure.

ALLOW EXCEPTIONS (a block rule may match but the action is benign, so allow:)
- Installing or updating a dependency already pinned in the project's manifest
  (package.json / go.mod / requirements.txt / Pipfile) with no other side
  effect.
- Pushing to the session's own working branch or a feature branch the user named.
- Pure read-only inspection (ls, cat, git status / log / diff, grep, ...) —
  these are already auto-allowed by policy and normally never reach this gate.
